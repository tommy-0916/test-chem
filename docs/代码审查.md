## 代码审查报告

### 审查目标
- 类型：Device Agent v2 验收复核
- 范围：Research Macro Plan 到 Device workflow 的参数映射、物理执行约束、近似方案审批和版本状态
- 说明：本报告按更完整的“通用参数映射与真实执行安全”口径复核，取代上一份仅针对同步加液特例的 `Approved` 结论。

### 严重问题

1. **通用参数误拒绝仍然存在。** `device_agent/single_agent.py` 仍把 LLM 返回的普通 `device_feasibility_error` 直接归为 `physical_infeasible`；当前补丁只按少量关键词识别同步加液特例，没有把 Macro 参数确定性分类为可下发字段、固定设备能力、派生/流程约束、离线条件或真正不可控条件。复现中，“Cu Kα 和 2θ 起止角没有独立下发字段”仍会导致整段方案被拒绝。
2. **最终 workflow 缺少确定性参数校验。** 成功路径只检查 `workflow_txt`、`steps` 列表和模型自报的 self-check；本地生成器也只校验步骤号、工作站和操作是否存在。复现中，包含未知参数 `不存在的危险参数=999` 的步骤仍被接受为 `success`。这不满足真实化学设备所需的 required/type/unit/range/enum/unknown-field 严格校验。
3. **近似执行没有审批门。** 同步加液被改写为交替批次后虽然标记 `execution_fidelity=approximated` 和 `requires_scientific_review=true`，但 `orchestrator/runner.py` 对所有 `status=success` 直接调用执行适配器，没有读取审核标记。当前“需要复核”只是元数据，不会阻止执行。

### 建议修改

- 为每个 Macro 要求生成结构化 `parameter_mapping`：记录分类、设备字段/步骤、真源证据、保真度和验证结果。没有同名字段不应自动等于物理不可行；缺少固定能力证据时应进入 `manual_required/unverified`。
- 在执行入口前增加独立 schema validator，严格验证工作站、操作、必填参数、未知字段、类型、单位、范围、枚举、容器兼容性及状态转移。
- 将 `approximated`、`manual_required`、`requires_scientific_review` 设为强制阻断状态，只有显式审批后才能进入执行适配器。
- 补充 XRD 固定能力、派生摩尔比、重复洗涤/分批加液、未知字段、缺失必填字段、越界参数和真实设备缺失等回归测试。

### 版本与测试结论
- `origin/main` 与 `origin/dll_main` 的 Device 核心文件内容相同；仓库没有可识别的 Device v2 commit、tag 或版本字段。`after_boundary_repair_v2.json` 是运行产物，不是代码版本。
- 本地 `device_agent` 6 项测试和 `orchestrator` 9 项测试通过，但测试只覆盖特定时序补偿，不能证明通用参数映射和下发安全。

### 结论

### 离线复算验证(对 3 次全部 15 道失败题,补全+重校验)
- 总 dispatch_validation 错误 **1024 → 697,降 31%(327 条)**。`容器数量`(221条,最大宗)
  等机械缺失被清零。
- 但 **0/15 题仅靠补全就转 passed**。诚实结论:真实运行里 Device 生成的 workflow 除机械缺失外,
  **还有大量深层结构错误**——核心是加液操作用平铺参数 `原液编号`/`原液量`/`批次序号` 描述,
  而 SKILL 要求嵌套 `加样方案` 数组结构。这类错误**不是补全能修的**(需 Device 提示工程),
  也不该硬编码去猜(遵循"只补确定性字段"的选择)。

### 结论
补全达到了设计目标:把 harness 自己能确定填的填了(降 31% 错误、免 LLM 自修复轮),让 Device
只需专注真正需要它的结构化字段。但它**单独不足以**让真实八题转 success——Device LLM 的加液结构
生成质量是**下一轮**要解决的(提示工程 + 加液结构的确定性组装),不在本轮"只补确定性字段"范围。

### 修复自身 wiring bug:补全未作用于 self-repair(attempt-2)输出
真实重跑 A01 时发现:dispatch_completion=0 但仍缺 保留瓶盖(机械字段)。定位到
`_repair_validation_failures` 的自身 bug——补全只在 attempt-1 跑;当结构错误触发 LLM 自修复轮后,
attempt-2 的新输出**未再跑补全**就直接校验,于是 attempt-2 重新引入的机械缺失(如 保留瓶盖)
没被补上,最终包展示的是 attempt-2(0 补全)。修复:抽出 `_apply_deterministic_completion` 助手,
attempt-1 与 attempt-2 都调用(dispatch_completion 跨轮累计)。回归测试
`test_completion_applies_to_self_repair_output`:attempt-1 结构错→触发修复→attempt-2 缺 保留瓶盖→
补全填=1→转 success。
